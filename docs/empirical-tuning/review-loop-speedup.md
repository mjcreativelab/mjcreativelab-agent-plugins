# レビュー雛形高速化（Issue #107）— Phase 1 ベースライン記録

対象: claude 系レビューループ（`sir-claude-review-set` / `sip-plan-review-set`）と単発敵対レビュー（`cra-claude-judge`）の構造並列化・差分スコープ化（Phase 2）に対する、変更前ベースラインの記録。

記録日: 2026-07-18（Issue #107 Phase 1）

## 計測方法と制約

- 過去セッションの Workflow 実行記録（journal.jsonl / エージェント transcript の mtime）を走査した。`sir-claude-review-set` の実行記録は 1 件（2026-07-14・Issue #88 セッション・**標準モード**）のみで、敵対モードのクリーンな実測は存在しなかった
- 見つかった標準モード実行はレビュワー r1 エージェントが 06:43 開始 → 09:00 終了（約 2 時間 17 分。API リトライ・キュー待ちを含むためステージ純所要時間としてはノイズが大きい）。**発見フェーズ（レビュワー / Breaker）が長極**であることの傍証にはなるが、定量ベースラインとしては採用しない
- したがって Phase 1 ベースラインは**直列スロット数・ステージ構造の定性比較**で記録し、実ウォールクロック短縮の定量実測（受け入れ基準の「目標 30% 減」）は**次回の本番レビューループ実行（dogfooding）に委譲する**。dogfooding 時は各ステージの `[HH:MM JST]` ログ（Issue #122 以降は `[YYYY-MM-DD HH:MM:SS JST]`）と journal.jsonl からステージ別所要時間を採取し、本ファイルに追記する

## 構造ベースライン（変更前）

敵対モード 1 セット（ラウンド 2 収束の典型ケース）の逐次チェーン:

```
audit → breaker r1 → judges r1(バッチ並列) → fix r1 → breaker r2 → judges r2 → probe-cleanup → 最終QA
```

- **直列スロット数: 8**（audit はループ前に直列 1 スロット）
- 最重量スロットは Breaker（effort max・6〜7 攻撃観点を単独で横断 + 反例テスト作成・実行）。ラウンドごとにフル攻撃面を走査する
- Judge のバッチ並列化（≤4 件/バッチ・`parallel`・effort high）は Issue #88 で導入済み（このスロットは既に「最も遅いバッチ」時間）
- `cra-claude-judge`（単発）: breaker → judge の直列 2 スロット。judge は「バッチ裁定 + Breaker 見落とし探索」を 1 体で兼務（effort max）し、Issue #88 でストール要因と特定された広域探索を含む

## 変更後の構造（Phase 2 実装。2026-07-18）

```
[breaker r1: レンズ S ∥ C ∥ O]（S は監査を内蔵） → judges r1(バッチ並列) → fix r1
  → [breaker r2: レンズ S ∥ C ∥ O・差分スコープ] → judges r2 → probe-cleanup → 最終QA
```

- **直列スロット数: 7**（独立 audit スロットをレンズ S に統合して消去）
- Breaker スロットの所要時間は「全観点の合計」→「最も遅いレンズ（観点 1/3 ずつ）」に変わる
- ラウンド 2+ の Breaker / レビュワーは直前ラウンドの採用修正差分に重点付け（差分スコープ化。ラウンド 1 の包括レビューが recall の backstop）
- `cra-claude-judge`: breaker → [judge バッチ群 ∥ miss-finder] の 2 スロット構造は維持しつつ、第 2 スロットが「バッチ裁定 + 見落とし探索の合計」→「max(最も遅いバッチ, miss-finder)」に変わる。miss-finder は diff スコープで有界化

### 期待される短縮の内訳（定性）

| レバー | 対象 | 期待効果 |
|---|---|---|
| レンズ分割並列化 | 雛形 B / sip の敵対 Breaker（全ラウンド） | 最重量ステージが並列化（効果大） |
| 監査役のレンズ S 統合 | securityAudit 時の初回セット | 直列 1 スロット消去（効果中・条件付き） |
| 差分スコープ化 | ラウンド 2+ の Breaker / レビュワー | 読込・probe 作成の対象縮小（効果大・r2+ のみ） |
| Judge バッチ + miss-finder 分離 | cra の第 2 スロット | 兼務の直列和 → 並列 max（効果中） |

## recall 比較の基準（A/B・dogfooding 用）

- 既知欠陥リスト: 初回 dogfooding 対象の diff に対する変更前雛形の確定指摘（真の欠陥）を基準セットとし、変更後雛形が同一 diff で同じ欠陥を検出することを確認する（Issue #107 受け入れ基準「既知欠陥の欠落なし」）
- 本セッションでは生ベンチマーク（実レビューループの新旧 2 回実行）を行わないため、基準セットは未採取。**dogfooding 初回実行時にここへ記録する**

## Phase 2 dogfooding 実測（2026-07-19）

Phase 1+2（PR #110）導入後、VTO PoC プロジェクト（別リポジトリ）で 2026-07-19 に dogfooding した（13 Workflow・対象リポジトリの Issue 789 / 790 / 791 / 796）。結果、**レビュー実施時間はほぼ変わらなかった**。実行ログの実測診断で、時間の支配要因は雛形の構造ではないと判明した。

### 時間が縮まなかった理由

1. **約 16 分の無応答ストール → 強制打ち切り → 直列リトライが実行時間を支配**
   - 失敗試行の署名は共通: ツール実行直後に次のモデル応答が返らないまま 15.8〜16.0 分沈黙 → ランタイムが打ち切り（記録上は interrupt マーカー）→ 同一呼び出しを最初から再試行
   - 13 Workflow 中 9 件でリトライ発生、2 件は全試行失敗（agent-failed）。sonnet / opus・役割を問わず発生しており、effort やプロンプト起因ではなく**ランタイム / API / ネットワーク層**の問題（社内プロキシによる長考中の無通信ストリーム切断を疑い）

   | 実行 | 呼び出し数 | 試行数（リトライ） | 浪費の目安 |
   |---|---|---|---|
   | 計画レビュー 789（180 分） | 6 | 14（+8） | 約 128 分 ≒ 7 割 |
   | 計画レビュー 791 set1（172 分） | 6 | 11（+5） | 約 80 分 |
   | 計画レビュー 790（169 分） | 6 | 11（+5） | 約 80 分 |
   | 実装フェーズ 789（180 分） | 5 | 10（+5） | 約 80 分 |

2. **実行はすべて標準モード（`-cldrl`）で、Phase 2 の主レバー（敵対 Breaker のレンズ分割）が非発動**
   - 標準モードのレビュワーは（当時）単発 1 体で 9 観点を横断していた
   - 差分スコープ化は有効に機能（ラウンド 1 が 30 分前後に対し、ラウンド 2 以降は 5〜13 分）

3. **収束の長期化 + セット間の人待ち**: 計画レビュー 791 は収束まで 8 ラウンド（ラウンド 7 まで新規指摘が出続けた）。セット間の続行確認待ちは最長 72 分

### 含意

- 速度の残り伸びしろはテンプレ外（ストール対策）にあり、プロンプト・構造の改修では取れない → 精度優先への転換は合理的
- ラウンド 7 まで新規指摘が出続けた実測は、「採用 0 が 1 回」での収束が変動（レビュワーの揺らぎ）でも成立してしまうことの証拠（Issue #111 で dry-twice 収束＝連続 2 クリーンに強化）

### この実測を受けた対応（Issue #111）

方針を速度優先から**精度優先**へ転換し、(1) 標準レビュワーの観点分割並列化（`sir-claude-review-set` / `sip-plan-review-set` を G1/G2/G3 の 3 グループ並列に）、(2) レビュー役のモデル opus 化、(3) dry-twice 収束（連続 2 クリーンラウンド）、(4) 敵対 Judge の effort max 化 を実装した。ストール自体はランタイム / プロキシ層の問題として本リポジトリ外（別トラック）で扱う。

## Phase 3（effort A/B）状況 — 取り下げ（Issue #111）

Issue #107 Phase 3（速度目的の effort A/B）は**取り下げ**た。2026-07-19 dogfooding で時間の支配要因が effort と無相関のランタイムストールと判明し（上記「Phase 2 dogfooding 実測」）、発見側 effort を `max` → `high` に落とす速度最適化は前提が崩れたため。Issue #111 は逆に発見・裁定側を opus 化・Judge effort を max 化した（精度優先）。「ストール率 × recall」測定としての再定義は優先度低（任意）。次回 dogfooding では recall・収束ラウンド数・ストール率を採取して本ファイルへ追記する。

## Issue #111 実使用フィードバックと再バランス（2026-07-20・Issue #113）

Issue #111（PR #112）の精度優先強化を実レビューループで使用した結果、次のフィードバックを得た:

- **以前より実施時間が長くなった**
- **起動するエージェント数が多く、トークン効率が悪い**

### コスト構造の診断

#112 は精度レバーを**全ラウンドに一律適用**していた:

1. 分割並列（標準 G1/G2/G3・敵対 S/C/O）が全ラウンド適用 — 差分スコープの軽量ラウンド 2+（実測 5〜13 分）でも 3 体が同じ context / diff を読み直す。トークン約 3 倍、16 分ストール（上記実測の時間支配要因）への露出も 3 倍
2. dry-twice 確認ラウンドもフル 3 並列 — バックストップ目的に包括ラウンド相当のコストを毎ループ支払う
3. Judge バッチの effort max — ≤4 件/バッチで作業量は有界（#111 自身が「有界化が本質対策で effort は無関係」と記録）で、max の上乗せ根拠が弱い

分割並列の recall 価値は「広い対象を深く見る」包括レビューに集中しており、対象が狭い差分スコープラウンドでは限界効用が小さい。

### 再バランス（Issue #113）

- **分割並列を包括ラウンド（初回セット round 1）限定に**: 差分スコープのラウンド 2+・確認ラウンド・継続セットは単発 1 体（`REVIEWER_ALL` / `LENS_ALL` = 分割定義の aspects 結合。union 不変を構造的に保証）
- **Judge バッチの effort max → high 戻し**（sir / sip / cra。miss-finder は max 維持）
- **維持**: レビュー役の opus・dry-twice 機構・差分スコープ化・レンズ S 監査統合・QA / probe-cleanup の sonnet

効果の見込み（標準・R1 実質 + R2 確認の典型ケース）: レビュー体 6 → 4。8 ラウンド型ロングループではレビュー体 24 → 10。ストール抽選への露出がエージェント数に比例して減る。

### 次回 dogfooding で採取するもの

- ループ全体の所要時間・エージェント数・リトライ（ストール）回数
- recall: 包括ラウンドの指摘の質、単発ラウンド・確認ラウンドでの追加検出有無（分割時代との比較）
- 収束ラウンド数（dry-twice の +1 ラウンドコストの実測）

## Issue #115 diff 正本化 — 計測待ち（2026-07-21 時点で実測値なし）

`sir-claude-review-set`（雛形 B）のレビュー役（レビュワー / Breaker / Judge）が各自で実行していた `git diff origin/<default>...HEAD` + `git status` + `git diff` を廃し、レビュー正本 `{作業Dir}/diff.md` の Read 1 回に置き換えた（生成: セット起動前 = オーケストレーター / ラウンド境界 = fix エージェント。鮮度ガード = 期待スタンプ `diffRound` の一致確認）。

**本 PR には実測値がない**。Issue #115 自身が「エージェント数 × diff 本文のトークンは渡し方を変えても消えない（それを減らすのは #113 のエージェント数削減）／本 Issue で取れるのは重複した git コマンド出力と取得作業のぶん＝中規模」と見積もっており、その見積もりの検証は次回 dogfooding に委ねる。以下は採取項目と方法のプレースホルダで、実測後にこの節へ追記する。

| 計測項目 | 採取方法 |
|---|---|
| レビュー役 1 体あたりの git ツール呼び出し回数（変更前は 3 前後 → 期待 0） | エージェント transcript の tool_use を `git diff` / `git status` で集計。`diff.md` の Read が 1 回入っていることも併せて確認 |
| レビュー役 1 体あたりの入力トークン | Workflow の journal / usage 記録をレビュー役ラベル（`reviewer:` / `breaker:` / `judge:`）で集計し、#113 時点の同種ラウンドと比較 |
| フォールバック発生回数 | レビュー役 transcript に `git diff` / `git status` の tool_use が残っているか（フォールバックの直接の痕跡）と、雛形 B の返却 `diffDegraded`（+ `dev fix r<N>: diff.md の再生成に失敗` ログ）の出現数。`diffRegenerated` は `required` のため、fix が返さずに取りこぼすことはない。レビュー役側の構造化出力に `usedFallback` は持たせていない（全レビュー schema の変更に見合わないため） |
| 鮮度ガードの誤検知 | クリーンラウンド / 確認ラウンドでフォールバックが起きていないこと（スタンプを進めない設計の妥当性確認） |

注意: 変更前後の比較は**同種のラウンド同士**で行う（包括ラウンドは 3 体並列、差分スコープラウンドは単発 1 体で、体数が違うと総トークンが比較できない）。

### #115 採取項目の回収（808 敵対・v117 実行より）

- レビュー役の diff 取得 git 呼び出し: **git diff 0 回**（変更前は 1 体 3 回前後）。Breaker は全員 `diff.md` Read 1 回。git status 0〜2 回は反例テストの変更セット確認用途で diff 取得ではない

- 真の recall（見逃し率）・指摘の正しさはログから測定できない（ground truth なし・対象 Issue も毎回異なる）。厳密比較は既知欠陥を仕込んだ empirical-prompt-tuning の A/B が唯一の手段（任意・未着手）

## Issue #122 プロンプト英語化 + 進捗・結果ログ強化（2026-07-24 実装・実測待ち）

構造（レンズ分割・バッチ並列・dry-twice・diff 正本・model / effort 割り当て）は不変。変更は表現と可視化のみ:

## Opus 過剰処理の抑制ノート RESTRAINT_NOTE（2026-07-27 実装・実測待ち）

Opus 化したレビュー役（#111）が過剰処理（サブエージェントの多量起動・冗長な出力）をする傾向への対処。[Prompting Claude Opus 5 ガイド](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5) の「Controlling subagent spawning」「Task scope and over-verification」「Written deliverable length」に基づき、4 スキル全雛形の `model: 'opus'` の全 `agent()` プロンプト末尾（`TAIL_NOTE` 直前）に共通の英語抑制ノート `RESTRAINT_NOTE` を追加した（resolve 雛形 A/B/D の 10 役・sip 4 役・cr 1 役・cra 3 役 = 18 箇所）:
