# Issue #115: レビュー雛形の diff 正本ファイル化（diff.md） — 実装ノート

日付: 2026-07-21（JST）
対象 Issue: #115（claude 系レビューループの各レビュー役が個別に実行していた `git diff` / `git status` の重複を排し、`{作業Dir}/diff.md` の Read 1 回に一元化する）
対象範囲: `smart-issue-resolve` の**雛形 B（`sir-claude-review-set`）のみ**。雛形 A / C / D / E・`smart-issue-plan`・`code-reviewer` / `code-reviewer-adversarial` は Issue 記載どおり対象外

## 自分で判断した事項

- **鮮度ガードは HEAD SHA ではなく「対象ラウンド」スタンプ**: 雛形 B の全エージェントはコミットしない（コミットはオーケストレーターの収束後経路のみ）ため、ループ中 HEAD は不変で round 2+ の変更はすべて未コミット。HEAD SHA の照合は今回防ぎたい失敗モード（fix 後の再生成漏れ）に対して検出力がゼロになる。SHA はヘッダに残すが診断用に留めた
- **スタンプの前進はスクリプト側で無条件**: `dev:fix-r<N>` を起動したら、その返却（`diffRegenerated`）や成否によらず `diffRound = N + 1` へ進める。自己申告に従うと「再生成していないのに一致扱い」で stale をレビューしてしまう。無条件前進なら再生成漏れは必ず次ラウンドの不一致になり、各レビュー役が自前 git 取得へフォールバックする（fail-safe）
- **クリーンラウンドではスタンプを進めない**: fix が起動されないラウンド（指摘 0 / 真の欠陥 0）では diff.md は変わらないため、進めると確認ラウンドで誤検知フォールバックが起きる。`diffRound` の前進は fix 起動時のみ
- **セット跨ぎ対策は「オーケストレーターが各セット起動前に必ず再生成する」不変則**: 前セット末尾がクリーンラウンドだと fix 由来のスタンプが新しい `startRound` に届かず、継続セット round 1 が必ずフォールバックになる。初回・継続・再起動を区別せず「起動直前に必ず生成」に統一した（`args` 契約は変更なし）
- **生成をアセットスクリプト（`assets/gen-diff.sh`）にした**: 理由は 3 つ。(1) fix プロンプトは js テンプレートリテラル内にあり、バッククォート・`${...}`・`$(...)` を含むコマンド列を直書きするとエスケープ事故を起こす（1 行の `bash ...` 呼び出しなら安全）。(2) round 1（オーケストレーター生成）と round 2+（fix 生成）で書式がドリフトしない — 鮮度ガードはヘッダ書式の安定に依存する。(3) レビュイー（dev）に書式の編集裁量を与えない（trust model の劣化を最小化する。プロンプトにも「diff.md を手で編集しない」と明記）
- **`gen-diff.sh` は `{作業Dir}` へコピーして使う**: fix エージェントは `{作業Dir}` しか知らず、スキルのインストールパス（`.agents/skills/...` 等）を解決できないため。出力先はスクリプト自身の `dirname "$0"` から解決し、引数は base ref と対象ラウンドの 2 つだけにした
- **`gen-diff.sh` の引数に Issue 番号を取らない**: 設計の書式例はヘッダに `（Issue #<番号>）` を含んでいたが、引数仕様は 2 つと定めていた。Issue 番号は同じ作業ディレクトリの `context.md` にあり重複情報のため、ヘッダから省いて引数 2 つの仕様を採った（Simplicity First）
- **diff 本文をコードフェンスで囲まない**: 本リポジトリの diff には 3 連バッククォートを含む行が日常的に出るため、フェンスだと入れ子が破綻する。`===== BEGIN/END COMMITTED DIFF =====` / `===== BEGIN/END UNCOMMITTED DIFF =====` マーカーで区切った
- **未追跡ファイルは一覧のみでスナップショットに内容を含めない**: サイズ肥大・バイナリ混入・生成コストを避ける。現行動作（`git diff` に未追跡の内容は出ない）とも整合し、実コード照合が必須のため Read で補える。プロンプトに「未追跡ファイルの内容と、生成後に作られた `.breaker-probe.` 反例テストはスナップショットに含まれない → 直接 Read する」と明記した
- **コピー元パスは相対パス優先 + Claude Code の展開を併記**: SKILL.md 手順 6-2 のコピー元は `assets/gen-diff.sh`（SKILL.md からの相対パス）を正とし、`${CLAUDE_SKILL_DIR}/assets/gen-diff.sh` に展開される旨を併記した。コピーに失敗すると全レビュー役がフォールバックして本機能が丸ごと無効化されるうえ、雛形 B は Workflow ツール前提＝ Claude Code でしか動かないため、確実に解決できる絶対パスを併記しても cross-tool 互換を損なわない（リポジトリ規約の「相対パスを基本にする」は維持）
- **再生成は「新規セットの起動前」に限り、`resumeFromRunId` の再開では行わない**: 当初は分岐を増やさない目的で「起動のたび常に再生成」に統一していたが、レビュー指摘で反例が出たため改めた。再開後のスクリプトは中断時点の `diffRound`（ラウンド進行に応じて前進済み）を保持しており、直前の `dev:fix` が再生成に成功していれば diff.md は既にその値で一致している。ここで `startRound` で作り直すとスタンプだけが巻き戻り、**再生成しなければ起きなかったフォールバックを残りラウンド全員に発生させる**（例: `startRound: 1` のセットで round 1 の fix 完了後に round 2 が `agent-failed` → 指示どおり再生成すると round 2・3 が全員フォールバックし、本 Issue の削減効果がセット全体で消える）。再生成しない側の危険（diff.md が stale / 不在）は従来どおりスタンプ不一致でフォールバックするため、安全側は保たれる
- **`diffRegenerated` は `required` にし、返却の `diffDegraded` へ伝播する**: 当初は「判定権はスタンプ側にあり観測用だから」と optional・ログのみにしていたが、雛形 B は劣化事象を必ず構造化返却で伝える設計（`auditFailed` / `judgeDegraded` / `breakerDegraded` / `reviewerDegraded`）であり、この経路だけ規約から外れていた。optional のままだと fix がフィールドを省略した場合に `=== false` が成立せずログすら出ず、効果測定の採取源も取りこぼす。`required` 化 + `diffDegraded` 返却に改めた。ただし他の `*Degraded` と違い**自動コミットは止めない**（レビュー品質は従来動作に戻るだけで、未探索・未裁定のような欠落が生じるわけではないため）
- **QA は diff.md 非依存に戻した**: 雛形 B の `qaPrompt` は従来 `diffNote` を共有していたが、独立 QA は「開発者の自己申告を信用しない」役割であり、レビュイーが生成したファイルに最終ゲートを依存させない。自分で `git diff origin/<default>...HEAD` と `git status` / `git diff HEAD` を実行する文言に戻した（雛形 A の QA・雛形 E は元から独立で無変更）
- **フォールバック・QA の未コミット取得は `git diff HEAD`（引数なしの `git diff` ではない）**: 正本 `gen-diff.sh` は `git diff HEAD`（index + worktree vs HEAD ＝ staged + unstaged）でスナップショットを作る。フォールバック文言を旧来の `git diff`（worktree vs index ＝ unstaged のみ）のままにすると、着手前に `git add` された変更が**フォールバックしたエージェントにだけ見えず**、レビュー走査範囲がラウンド・エージェントごとに変わる。`git status` は状態行のみで内容を出さないため補完にならない。雛形 B の `diffNote` フォールバックと `qaPrompt` を `git diff HEAD` に統一した（本セッションで空リポジトリに staged 変更を作り、`git diff` が空・`git diff HEAD` が差分を出すことを実測して確認）。雛形 A / C / E の同文言は本 Issue の変更対象外のため据え置き（従来どおりの挙動。是正するなら別 Issue）
- **`diffNote` の「読み方」は役割別に出し分ける**: レビュワー・Breaker は diff 全文を読む（見落としの単一障害点を作らないため）が、Judge は「ヘッダ + 変更ファイル一覧をまず読み、以降は担当バッチの evidence が指す箇所だけ offset 指定で読む」に切り替えた（`diffNote(expected, targeted)` の第 2 引数）。Judge は ≤4 件/バッチの**有界作業量**エージェントで、同じプロンプト内に「照合は evidence が指すファイル / 行に限定」「3 分以内に着実に tool を進める」（Issue #113 の無進捗ストール対策）があり、無条件の全文ページング読みはこれと相反する。変更前は各役が自分で `git diff` を実行しており、ハーネスの出力打ち切りが事実上の上限として働いていた点も考慮した。`gen-diff.sh` ヘッダの注記も「全文を読む」から「読む範囲は依頼元プロンプトの指示に従う」へ中立化した
- **レビュー役への「実コード照合」指示を維持・明文化**: diff.md は「どこを見るか」の入力にすぎず、判断根拠はリポジトリの実コードであることを `diffNote` に明記した（抜粋だけを渡すスカウト方式にすると、スカウトの見落としが全レビュワーへ伝播する単一障害点になる — Issue の方針 3）

## 採用しなかった代替案

- **レビュー役に diff.md の妥当性を検証させる**: 各エージェントで `git rev-parse` / `git status` が復活し、削減しようとしたトークンが戻る。スタンプ照合（Read 済みファイルのヘッダ 1 行）で追加コスト 0 にした
- **sip（`sip-plan-review-set`）への横展開**: レビュー対象が `plan.md` で既にファイル正本のため、重複する git 取得が存在せず削減余地がない。構造同期の例外として sip の同期ノート「同期しないもの」と CLAUDE.md マスターに明記した
- **cr / cra への横展開**: 単発スキルで `{作業Dir}` 機構を持たず、構造追加が本 Issue の想定を超える（必要なら別 Issue）
- **diff.md のサイズ上限・分割**: truncate はページングで対応する方針にし、上限設計は入れない（読む範囲の制御は役割別の「読み方」指示で行う。全文読みはレビュワー・Breaker のみ）

## トレードオフ

- **レビュー役がレビュイー（dev）の生成物に依存する**構造になり、敵対レビューの独立性がわずかに希薄化する。緩和として (1) dev は固定スクリプトを実行するだけで書式の編集裁量がない、(2) 実コード照合の必須指示を維持、(3) 最終ゲートの独立 QA は非依存、(4) スタンプ不一致で自前 git へフォールバック、を組み合わせた
- **削減効果は中規模**（Issue 自身の見積もり）。エージェント数 × diff 本文のトークンは渡し方では減らない（減らすのは #113 のエージェント数削減）。取れるのは重複した git コマンド出力と取得作業のぶん
- **`gen-diff.sh` のコピーに失敗する環境**では diff.md が存在せず全レビュー役がフォールバックする ＝ 変更前と等価な動作に degrade する（機能は落ちない）
