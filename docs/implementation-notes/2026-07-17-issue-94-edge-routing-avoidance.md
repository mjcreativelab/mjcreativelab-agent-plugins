## Step 3 報告（本格ルーティング＝障害物回避の要否判断）

**結論: 本格ルーティング（障害物回避）は必要**。軽量迂回（スーパーグラフのダミー中継流用）は本フィクスチャ群で node 交差削減 0（9→9）、frame 交差削減 1（2→1）にとどまり、費用対効果はほぼ無い。

残存 9 件の node 交差の根本原因と、解消に必要な機構:

- **sibling 6 件（支配的）**: グループ間エッジが幅広フレームの奥にあるノード（例: worker は gcp 右端）から出てフレーム全体を横断して隣接グループへ向かう際、同一グループの兄弟ノードを横切る。フレーム**内**の交差であり、フレーム**間**の隙間に置くダミー中継では原理的に回避不能。→ 同一グループ内の障害物回避（ノードを避けて枠境界へ抜ける経路）が必要。
- **unrelated 1 件**: 共有ダミーが通過先フレーム（infra）の下に置かれる一方、宛先（booking）が枠上部にあるため、戻り線分が infra 列を縦断して mailer を掠める「V 字」。単一ダミーの軽量迂回では防げない。→ 通過フレームに対する真の障害物回避が必要。
- **flow 2 件**: flow モードのダミー配置由来（sessions→users のダミーが orders を掠める）。Step 2 は flow モードを変更しないため対象外。→ flow レイアウトのダミー配置改善（別スコープ）。

**なぜ軽量迂回が効かないか（構造的理由）**: スーパーグラフは多くの場合「平坦」（各グループが隣接カラム＝どのスーパーエッジも 1 レイヤーしかスパンしない）で、ダミー中継が 1 つも生成されない。infra-areas は全グループ間エッジが 2 点直線で迂回は完全な no-op だった。ダミーが生成される多層ケース（component-areas の app→domain）でも単一ダミーの V 字が新たな交差を作り、frame 交差が 1 減った一方 node の unrelated 交差は移動しただけ。

**推奨**: Step 1 の資産（`__SV_DEBUG__.edges` + 交差ハーネス）は本格ルーティングの進捗計測にそのまま使えるため残す価値が高い。軽量迂回（Step 2.1）はラベル修正後に回帰が無く無害。(i) Step 1+2 を忠実実装として維持し本格ルーティングを後続 Issue 化する、または (ii) Step 2.1 を revert して full-routing 設計に直行、のいずれか。効果の薄さと後続の設計自由度からレビュー判断に委ねる（当方の傾きは (i)）。
