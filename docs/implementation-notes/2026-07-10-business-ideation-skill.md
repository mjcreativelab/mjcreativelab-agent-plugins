# 実装ノート: business-ideation スキル新規作成（2026-07-10 JST）

ビジネス・サービスのアイデアを「発散 → 深掘り → 評価」で練る汎用スキルの新規作成。
素材: [phuryn/pm-skills](https://github.com/phuryn/pm-skills)（8 プラグイン・約 60 スキル）と near-fashion-business-ideation プラグイン（社内・特定ドメイン向け立案パイプライン）から、効果の高い要素を調査・選抜して統合した。

## ユーザー決定事項（AskUserQuestion で確認済み）

| 論点 | 決定 |
|---|---|
| スコープ | 汎用（ドメイン非依存）。NEAR FASHION / ZOZO 固有の戦略・数値・FMT は除去 |
| カバー範囲 | 発散〜評価まで（リサーチ・構造化・GTM はスコープ外） |

## 調査プロセス（Workflow 並列調査）

- 両ソースを 9 グループに分割し、並列読解 → 統合レポート生成の Workflow で調査（約 150 要素を抽出・must-have 判定）
- 実行中に API 接続断・セッションリミットで 2 回失敗。完了済みグループの結果を journal.jsonl から回収し、欠損 3 グループのみ再実行する継続 Workflow で復旧
- `nf-eval-research`（評価スコアカード詳細）は subagent が 2 回連続で接続断となったため、`near-fashion-evaluation/SKILL.md`（533 行）をメインセッションでインライン読解して補完
- `nf-later-phases`（structuring / GTM / KPI / M&A の詳細）は最終的に**未読のまま採用判断した**。理由: いずれも「発散〜評価」のスコープ外の後工程で、統合レポートが pipeline-overview 経由で必要要素（差し戻しルーティング・handoff manifest 等）をカバー済みのため

## 仕様に明記がなく自分で判断した事項

1. **★1〜5 採点を廃止し 3 値判定（強/弱/不明）+ 根拠 1 文に変更** — アイデア段階の数値はすべて仮説値であり、精密採点は疑似定量化（幻覚数値に精密さの衣を着せる）になるという統合レポートの判定を採用
2. **ビーチヘッド 4 基準を評価フェーズでなく Phase 2-4（顧客の絞り込み）に配置** — 統合レポートは evaluation 側にランクしていたが、「勝てるシェア」等の定量制約はセグメント選定時に使う方が発散膨張を早く潰せると判断
3. **North Star Metric 7 基準は独立セクションにせず、KSF の「KPI に落とせる粒度まで具体化」ルールに吸収** — Quick/Full 両モードで装置数を抑えるため
4. **ZOZO 固有の Gate 条件 4 項目は「Phase 0 でユーザーが定義するガードレール」の all-or-nothing ゲートに汎化** — 構造（事前定義 → 評価冒頭で全通過必須 → ⚠️ は設計変更合意まで進行不可）だけ移植し、中身をユーザー入力化
5. **`disable-model-invocation: true` を付与** — 当初は「副作用は notes 作成のみで Phase 0 で場所確認するため不要（自動起動の利便を優先）」と判断したが、レビューで「リポジトリ内の Write / Edit を allowed-tools に持つ 9 スキルすべてが `disable-model-invocation: true` で統一されており本スキルだけ例外になる」「無関係リポジトリでの雑談的発話から自動発火し許可プロンプトなしで docs/ 配下にファイル作成が起きうる」との指摘が確定し、判断を撤回してリポジトリ慣行に合わせた（description のトリガー文言は smart-commit 同様、他エージェント向けに残置）
6. **数値台帳は ID 採番なしの最小形**（numbers-registry の整合チェック機構は移植しない）
7. **SKILL.md は想定 330 行 → 実際 160 行** — フェーズ詳細を references に寄せた結果。500 行制限に対して意図的に余裕を持たせた
8. **並列ワーカー機構・商標スクリーニング・クロスモデルレビュー・Confluence/Jira 連携は不採用** — 統合レポートの「落とす」判定どおり（汎用スキルには過剰装備・環境依存）
