# notes / summary テンプレートと見出し規約

ドキュメント正本方式の実装仕様。notes が正本、会話はワーキングメモリ、summary は確定結果の抽出。

## ファイル配置

```
docs/business-ideas/<テーマスラグ>/
├── notes.md      # 検討の正本（追記で育てる。初期雛形は assets/idea-notes-template.md）
└── summary.md    # 完了時に生成する最終サマリ
```

- テーマスラグは kebab-case（例: `senior-solo-living-services`）
- 置き場所は Phase 0 でユーザーが変更してよい（変更したら notes 冒頭に記録する）

## notes の見出し規約

- **フェーズ確定**は必ず `## Phase <N> <フェーズ名> 確定（YYYY-MM-DD）` の H2 で書く（フェーズ名: `前提` / `発散` / `深掘り` / `評価`）。この見出しの存在が次フェーズへの物理ゲートになる
- 検討途中の素案・論点は `## <案ID> 検討メモ: <トピック>` の H2 で追記する（確定と素案を見出しレベルで区別し、`grep '^## '` で機械抽出できる状態を保つ）
- 確定済み内容の訂正・前提変更は `## Phase <N> <フェーズ名> 訂正（YYYY-MM-DD）` の H2 で追記する（元の確定セクションは書き換えない。変更内容・ユーザー確認の結果・波及範囲を記す）
- 過去の記述は消さない・書き換えない。訂正・昇格は追記で行う（evidence-rules.md「ラベルの昇格」）
- 深掘り対象が複数案あるときは、案ごとに `### 案 <ID>` の H3 で区切る

## handoff manifest（申し送り表）

フェーズ確定セクションの末尾に必ず置く。**空欄禁止 — 該当がなければ「該当なし」と明記する**（空欄は「検討していない」と「該当なし」を区別できない）：

```markdown
#### handoff manifest
| 項目 | 内容 |
|---|---|
| 未確定の前提 | <ユーザー確認待ち・未定のまま進めた前提> / 該当なし |
| 推計のままの数値 | <`推計` ラベルのまま判断に使っている数値> / 該当なし |
| 規制・コンプライアンス論点 | <⚠️ 以下の判定と確認先> / 該当なし |
| 未解決論点 | <議論したが決着していない論点> / 該当なし |
| 次フェーズへの注意 | <次フェーズが誤読しそうな箇所への注記> / 該当なし |
```

manifest に「未確定の前提」「推計のままの数値」が残っていても次フェーズへ進んでよい（明記されていることが条件）。ただし規制論点の ❌ 疑いだけは進行不可（SKILL.md 横断ルール 5）。

## ユーザー判断待ちセクション（中断・再開）

セッションを中断するとき、notes 末尾に以下を残す（再開時はここから読む）。**このセクションは常に最新 1 つだけ**を維持する（解消したら見出しごと削除してよい — 唯一の例外的な削除）：

```markdown
## ユーザー判断待ち（YYYY-MM-DD 時点）
- 現在地: Phase <N> の <手順番号> まで完了
- 判断待ち: <ユーザーに確認したいこと（選択肢があれば列挙）>
- 保留中の作業: <判断後に再開する作業>
```

```markdown
## 数値台帳
| 数値 | 採用値 | レンジ | ラベル | 前提・出典 | 使用箇所 |
|---|---|---|---|---|---|

| 想定客単価（月次/年次） | | | | | |
| WTP | | | | | |
| CAC / LTV | | | | | |
| Kill line 閾値 | | | | | |
```

## summary.md の書式

完了時に notes から確定内容だけを抽出して生成する（12 セクション固定 — 比較可能性と「どこまで埋まったか」の判定のため）：

```markdown
# <案名（仮称）> — 検討サマリ（YYYY-MM-DD）

> 本ドキュメントの名称はすべて仮称。正式な商標・ドメイン調査は別途必要。

1. ## 一言説明          — 誰のどんな困りごとを何で解決するか（1〜2 文）
2. ## 問題と課題実在性   — Job Story 1 文 + 放置コスト / 現状ワークアラウンド / Before-After
3. ## 顧客              — ビーチヘッドセグメント + 失格基準（誰が顧客でないか）
4. ## 価値提案          — 6 パーツ（Who/Why/Before/How/After/Alternatives）+ Aha moment
5. ## 事業構造          — 構造類型 / フライホイール / KSF（1〜3 個、KPI 粒度）
6. ## Why Now           — 1 文言い切り + 根拠となる追い風
7. ## 収益モデル        — 3 分類 / WTP / LTV・CAC 桁感 / やらないこと（Trade-offs）
8. ## 評価サマリ        — 観点別 3 値判定表（強/弱/不明 + 根拠 + 証拠ラベル）
9. ## 検証プラン表      — XYZ 仮説 / 証拠ラベル / 最安の検証方法 / 成功閾値 / 反証されたら何が崩れるか
10. ## Kill line と Decision Framework — 撤退基準（数値・期限）+ 成功なら→/失敗なら→
11. ## 数値台帳（抜粋）  — 判断に使った主要数値と根拠
12. ## handoff manifest — 未確定の前提 / 推計のままの数値 / 規制論点 / 未解決論点（空欄禁止）
```

セクション 9・10・12 が埋まっていない summary は生成しない（SKILL.md「完了の定義」）。Quick モードやユーザー判断でスキップした手順に対応するセクション（例: Quick では 3・4・5・8）は、**捏造せず本文を「未実施（Quick モード）」の 1 行にする**（見出し自体は 12 セクションのまま削らない — 「どこまで埋まったか」を判定可能に保つため）。部分的に実施したセクション（例: Quick の 7 収益モデルは 3 分類と WTP のみ）は、実施分を書き、未実施の項目にのみ「未実施」を注記する。
