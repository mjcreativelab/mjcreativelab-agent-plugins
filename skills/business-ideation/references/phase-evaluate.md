# Phase 3: 評価・ストレステスト — 手順詳細

Phase 2 を確定した案ごとに 3-0 → 3-8 を進める。ここからは姿勢を反転する: **根拠なく褒めない**。ただし疑念の捏造もしない — 本当に良くできている点は「良くできている」と明言する（これがないと指摘全体が信頼を失う）。

**Quick モードの必須セット**: 3-0 / 3-1（3 件上限）/ 3-6 / 3-7。それ以外はユーザーが求めた場合のみ実施する。ただし評価の過程で ❌・弱・Kill 基準への抵触が出た場合は、モードによらず 3-8（差し戻しルーティング）を必ず実施する（弱い案を弱いまま summary に流さないため）。

判定はすべて **3 値（強 / 弱 / 不明）+ 根拠 1 文 + 証拠ラベル**で書く。★ 5 段階などの精密採点はしない — アイデア段階の数値はすべて仮説値であり、精密な点数は幻覚数値に精密さの衣を着せるだけになる。

## 3-0: ガードレールゲート（all-or-nothing）

Phase 0 で確定したガードレール（やらないこと・守るべき制約）それぞれについて `✅ 適合 / ⚠️ 要検討 / ❌ 抵触` を判定し、根拠を 1 文書く。

- **全 ✅ でなければ次に進まない**。⚠️ は「✅ に変えるための設計変更 or 追加確認」をユーザーと合意してから再判定する。セッション内で解消できない ⚠️（外部確認待ち等）は、ユーザーが明示的に受容した場合のみ manifest の規制・未解決論点に記録して先へ進んでよい（❌ は不可）
- Phase 1 の法規制スクリーニングで ⚠️ が残っている場合、ここで再確認する。**❌（事業の根幹に抵触する疑い）は件数を問わず進行不可** — 回避設計を作り直すか、専門家確認を経るまで Phase 3 を進めない
- ⚠️ / ❌ には分類ラベルを付ける: **Evidence Gap**（データ不足が主因）/ **Structural Weakness**（構造・仮説の弱さが主因）/ **Legal Blocker**（法規制リスクが主因）。3-8 の差し戻し先判定に使う

## 3-1: Red-team（急所仮説への攻撃）

Pre-mortem との役割分担: **Red-team は生きている仮定を「今」攻撃する。Pre-mortem（3-2）は失敗を既成事実として物語り、逆算する。** 両方やる場合も先に Red-team。

1. **急所主張（load-bearing claim）の抽出**: notes からこの案が「真」として主張していること（顧客・市場・仕組み・タイミング・数値）を列挙し、**それが偽なら案が死ぬもの**だけに絞る。化粧的な主張は攻撃しない
2. **Steelman してから攻撃する**: 各急所主張について、まず「それが真である最強の理由」を述べてから、**その最強版を**攻撃する。弱い版への攻撃は無価値
3. **反証可能な形で書く**: 失敗モードは「**Fails if ___**（〜なら破綻する）」形式で具体的・検証可能に書く。「実行リスクがある」のような抽象論は書かない
4. **ランキング**: （外れたときの影響）×（外れている確率）×（検証の安さ）でランク付けし、**上位 3〜5 件に絞る**（Quick は 3 件）。20 個の一般論より 5 個の本物の急所
5. **各急所仮説に 4 点セット**を付ける:
   - **Fails if**: 案が破綻する具体的な条件
   - **今週集められる証拠**: それを最も安く確かめるデータ・会話・行動
   - **Kill 基準**: この閾値を割ったら方向転換する、という値
   - **最安のテスト**: 信念を動かせる最小の実験
6. **捏造禁止・両論併記**: 案が既に十分な根拠を持つ主張には「これは良く出来ている」と明言する。出力の末尾に「**良くできている点**」「**評価できなかった点**（判断材料が足りなかった箇所）」を必ず設ける

## 3-2: Pre-mortem（事前検死）

「3 年後（副業なら 1 年後など、案の時間軸に合わせる）、この事業は失敗した」と既成事実化して逆算する：

1. **死因候補を 7〜10 件**列挙する（「ありうる」レベルの具体性で）。典型カテゴリを一次プロンプトに使う:
   - ターゲットを取り違えていた / 課題が思ったより浅かった
   - 構造的優位性がなく、競合・大手に追随されただけだった
   - ユニットエコノミクスが回らず、成長するほど赤字が膨らんだ
   - 法規制・プラットフォーマーの方針変更で土台ごと崩れた
   - 獲得チャネルが見つからず、初期ユーザーから先に広がらなかった
   - 新しい概念が形成できず「何のためのサービスか」が伝わらなかった
   - 複数ステークホルダーの片側最適化で、批判・信頼毀損につながった
   - 体験品質のばらつきが大きく、初回の失望でリピートが崩れた
   - 推進者の時間・意欲・キーパーソンが持たなかった
   - 既存事業・本業との利益相反で推進が停滞した
2. **三分類**する（リスクリストの水増し防止と、暗黙の不安の炙り出し）:
   - **Tigers**: 根拠・経験・明確な論理に基づく本物のリスク → 対策必須
   - **Paper Tigers**: 心配されがちだが過大評価と判断するもの → 理由を書いて置いておく
   - **Elephants**: 誰も口にしていないが検討されていない不安 → 調査対象に昇格
3. Tigers を **発生確率（高/中/低）× 致死性（畳むレベル / 撤退判断レベル / 計画修正レベル）** で評価し、トップ 3 に**予防策を 1〜2 件ずつ**書く
4. **予防策のうち検証可能なものは 3-6 の検証プラン表に還流させる**（書いて終わりにしない）

## 3-3: 模倣シミュレーション

- 「資金力のある競合 2〜3 社が、明日このコンセプトをそのまま発表した」と仮定し、**競合側の手番を 2〜3 手**具体的に走らせる（価格を下げる・既存顧客基盤に同機能を配る・供給側を囲う 等）
- そのシミュレーション後も**こちらに残る要素だけ**を構造的優位性と認める。機能差・UI の良さは優位性に数えない
- **Can't / Won't テスト**: 競合が「コピーできない理由（Can't: データ・資産・規制・関係性）」または「コピーしない理由（Won't: 彼らの既存事業と食い合う等）」を言語化できるか。どちらも言えない場合、優位性は「先に始めた」だけ — その旨を弱として記録する

## 3-4: 整合チェック

戦略要素が互いに矛盾していないかを、矛盾が出やすいペアで点検する：

| ペア | 典型的な矛盾 |
|---|---|
| 単価 × 獲得チャネル | 低単価なのに人手営業・高 CAC チャネル前提 |
| セグメント × チャネル | ビーチヘッドがいない場所で獲得しようとしている |
| コスト構造 × 価格 | 原価・オペレーションコストに対して価格が構造的に薄い |
| 品質約束 × 供給構造 | ユーザー供給（CtoC）なのに均質な品質を約束している |
| 成長速度 × 資金 | フライホイールが N 周目から加速する設計なのに初期資金計画がない |

矛盾が見つかったら、どちらの要素を直すかを議論して notes を更新する。

## 3-5: 評価サマリ（3 値判定）

ここまでの結果を観点別にまとめる。**3 値（強 / 弱 / 不明）+ 根拠 1 文 + 証拠ラベル**。**弱 / 不明の行には分類ラベル（Evidence Gap / Structural Weakness / Legal Blocker）を併記する**（3-8 の差し戻し判定の入力になる）：

| 観点 | 判定 | 根拠（1 文） | 証拠ラベル | 分類ラベル（弱/不明のみ） |
|---|---|---|---|---|
| 課題の実在性 | 強/弱/不明 | | | |
| 顧客の絞り込み（ビーチヘッド） | | | | |
| 提供価値と代替手段への優位 | | | | |
| 事業構造（フライホイール・KSF） | | | | |
| Why Now | | | | |
| 収益モデル（LTV/CAC 桁感） | | | | |
| 構造的優位性（模倣後残存） | | | | |
| 整合性 | | | | |

未実施の手順に依存する行（例: 模倣シミュレーション未実施なら「構造的優位性」）は判定せず「未実施」と書く。「不明」は恥ではなく検証プラン行きの入力。**不明を弱や強に丸めない。**

## 3-6: 検証プラン表

実施した手順の出力 — Red-team の 4 点セット（常にある）、実施していれば Pre-mortem の予防策・2-9 の低確信度仮定 — を **1 つの検証プラン表**に統合する：

| 仮説（XYZ 形式） | 現在の証拠ラベル | 最安の検証方法 | 成功閾値（事前宣言） | 反証されたら何が崩れるか |
|---|---|---|---|---|
| 少なくとも <Y> の <X>% が <Z> する | | | | |

- **XYZ 形式**（「少なくとも Y のうち X% が Z する」）で書けない仮説は、まだ検証可能になっていない — 書ける形まで具体化する
- **最安の検証方法**は行動データが取れるものを優先する（意見より行動）: ランディングページ + 登録、説明動画 + 反応率、ウェイトリスト / 先行予約（お金・時間を賭けさせる = Skin-in-the-Game）、手作業で価値を届けるコンシェルジュ型 MVP 等
- **成功閾値は実験の前に宣言**し、notes に書いてから実験する（後から都合よく解釈しない）
- 「反証されたら何が崩れるか」列が**急所仮説の特定を強制する** — 何も崩れない仮説は検証の優先度が低い

## 3-7: Kill line と Decision Framework

アイデアに惚れ込む前に、撤退条件を数値で事前に握る：

- **Kill line**: 「<期間> で <指標> が <閾値> に届かなければ、この案は進めない」形式で 1〜3 本。数値・期限のない Kill line は Kill line ではない
- **Decision Framework**: 検証プラン表の主要行それぞれに「成功なら → <次の行動>」「失敗なら → <ピボット方向 or 撤退>」を事前にコミットする
- **この 2 つが空欄のまま「完了」と見なさない**（SKILL.md の完了定義）

## 3-8: 差し戻しルーティング

評価で弱 / ❌ が出た案を、弱いまま summary に流さない。3-0 で残った ⚠️ と 3-5 の弱 / 不明の行に付けた分類ラベルを集計して戻し先を決める（Quick で 3-5 を実施していない場合は、Red-team で Kill 基準に抵触した急所仮説とガードレールの ⚠️ に同じ分類ラベルを付けて判定する）：

| 多数派ラベル | 診断 | 戻し先 |
|---|---|---|
| Evidence Gap | データ・裏取り不足 | 「追加調査すべき項目リスト」を notes に書き、ユーザーに調査を提案（このスキルの範囲外）。調査後に 3-5 から再判定 |
| Structural Weakness | 構造・仮説そのものの弱さ | Phase 2 の該当ステップ（構造類型・KSF・収益モデル）へ差し戻し。案の根本が弱ければ Phase 1 の見送り案・再発散へ |
| Legal Blocker | 法規制リスク | 進行不可。回避設計の再構築 + 専門家確認先の明記が済むまで先に進めない |

拮抗している場合は Phase 1 から組み立て直すことを推奨する。**差し戻しはこのスキルの失敗ではなく正常な出力** — 弱い案を早く安く殺せたこと自体が成果。

## Phase 3 の出口

1. notes に「## Phase 3 評価 確定（YYYY-MM-DD）」セクションを書き出す。常に必須: Red-team 上位・検証プラン表・Kill line。実施した場合のみ: 3 値判定サマリ・ルーティング結果（未実施は「未実施（Quick モード）」と明記）
2. note-templates.md の書式で `summary.md` を生成する
3. handoff manifest を最終更新する（空欄禁止）
4. 次の一手 2〜3 個を、評価の最重要発見に基づいて動的に提案して完了
