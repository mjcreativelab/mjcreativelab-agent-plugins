# Phase 2: 深掘り — 手順詳細

Phase 1 で選定した案ごとに 2-1 → 2-9 を進める。複数案あるときは 1 案ずつ完了させる（並行して混ぜない）。
確定した内容は都度 notes の当該案セクションに追記する（見出し規約は note-templates.md）。

**進め方の姿勢**: このフェーズでは案を否定・採点しない。「なぜそう思うのか」「他の手段ではダメなのか」を繰り返し聞いて解像度を上げる。ただし質問攻めにしない — 1 メッセージ 1 論点で、ユーザーの回答に含まれる仮定を言語化して返す。

**Quick モードの必須セット**: 2-1 / 2-3 / 2-7 / 2-8（3 分類と WTP アンカーまで）。それ以外はユーザーが求めた場合のみ実施する。

## 2-1: 問題ファースト変換

アイデア（解決策）から入っていても、まず**どの問題の解決策なのか**に変換する：

- 「このアイデアは、誰の、どんな問題の解決策か」を**当事者の一人称**で書く（例: 「私は毎週◯◯に 2 時間かかっていて、□□できないのがつらい」）
- Job Story 1 文で書けるか診断する: 「<状況>のとき、<動機>したい。そうすれば<期待する成果>できる」。**この 1 文が書けない・書いても空虚な場合は顧客理解不足のサイン** — 2-2 / 2-3 で埋めてから戻る

## 2-2: JTBD（Jobs to Be Done）三層分解と市場カテゴリ再定義

ユーザーは機能ではなく「片付けたい用事（Job）」のためにサービスを雇う：

| 層 | 内容 |
|---|---|
| Functional Job（機能的） | 客観的に達成したいタスク |
| Emotional Job（情緒的） | どう感じたいか（不安の解消・罪悪感からの解放など） |
| Social Job（社会的） | 周囲からどう見られたいか |

- **反実仮想の問い**: 「このサービスが使えなかったら、ユーザーは何で同じ Job を片付けるか？」— 競合は同業他社ではなく **Job を片付ける別の手段全般**（何もしない・手作業で凌ぐ・隣接サービスで代用する等）
- **市場カテゴリの再定義**: 既存の業界名で市場を固定しない。Job / ペイン起点で必要なら新しいカテゴリとして切り直す（物理業態ではなく「得られる成果」で切る）。市場母数はそのペインを持つ人・世帯・企業の数から再推計し、**SOM（実際に取れる市場）は運営人員・供給者数・配送枠などの物理・運用キャパ制約も反映**する

## 2-3: 課題実在性テスト 3 点セット

「あったら便利」を潰す最安のストレステスト。3 問すべてに具体的な答えを出す（答えられない場合、その旨を主張ラベル `要実確認` 付きで notes に記録する）：

1. **放置コスト**: この問題を解決しないと、誰に・いくらの損失（お金・時間・感情）が出続けるか
2. **現状ワークアラウンド**: 対象者は今日この問題をどう凌いでいるか。**なぜそれで我慢できているのか**（我慢できているなら、それを乗り越えるだけの差分価値が要る）
3. **Before / After ギャップの定量化**: 導入前後で何がどれだけ変わるか（金額・時間で）

## 2-4: 顧客の絞り込み

- 想定顧客を **3〜5 セグメント**に分け、セグメントごとにペインの深さ・支払い意思・到達しやすさを 1 行で比較する
- **失格基準（誰が顧客でないか）を必ず 1 行書く** — 「全員が顧客」は顧客理解ゼロと同じ
- **最初のセグメント（ビーチヘッド）を 4 基準で選ぶ**:

| 基準 | 問い |
|---|---|
| 燃える痛み | このセグメントは問題を「今すぐ」解決したがっているか |
| 支払い意思 | 実際にお金を払う予算・権限・前例があるか |
| 勝てるシェア | この狭いセグメントなら現実的な期間で過半のシェアを取り切れるか |
| 紹介性 | セグメント内で口コミ・紹介が回る接点があるか |

- 選定理由と、選ばなかったセグメントを「後回し」として notes に残す

## 2-5: 価値提案の状態遷移記述

6 パーツで書く。**Alternatives（代替手段）の名指しが最大の反証圧力** — 「競合はいない」と書きたくなったら 2-2 の反実仮想に戻る：

```
- Who: <ビーチヘッドセグメント>
- Why: <片付けたい Job（三層のうち中心のもの）>
- Before: <現状の状態・感情>
- How: <このサービスが介在する方法>
- After: <導入後の状態・感情>
- Alternatives: <ユーザーが比較する代替手段の名指し（無消費含む）>
```

- **Aha moment**: ユーザーが最初に「これだ」と感じる瞬間はいつ・何か。そこに到達するまでに何ステップ我慢させるか。ステップが多いほど離脱する — 減らせないかを議論する

## 2-6: 事業構造チェーン（構造類型 → フライホイール → KSF）

キャンバスの欄埋めではなく、**利益の源泉 → 必要なユーザー行動 → 障壁**という因果で構造を確定する。ここの認識がずれると収益モデル・KPI・打ち手がすべてずれるため、**構造類型はユーザーと明示的に合意**する。

### 2-6-1: 構造類型の特定

| 類型 | 特徴 |
|---|---|
| パイプライン型 | 一方通行の工程フロー（仕入れ → 加工 → 販売） |
| ハブ型 | 中心のホームポジションから複数の手段に行き来できる（双方向フロー） |
| プラットフォーム型 | 多面市場。供給側と需要側をマッチング |
| ネットワーク型 | ユーザー同士の接続が価値を生む |
| SaaS 型 | 継続課金。顧客のワークフローに組み込まれて粘着性を生む |

- ハブ型の「ホームポジション」は物理施設・画面とは限らない。ユーザーが繰り返し戻りたい**体験価値**を中心に置く
- 逆方向のフロー（返却・キャンセル・差し戻し）を必ず確認する — 一方通行の矢印だけで描かない
- マーケットプレイス・レンタル・シェアリング型のみ、供給構造（自社在庫 / ユーザー供給 / ハイブリッド）も選ぶ。供給構造はユニットエコノミクス（1 顧客あたりの採算構造）を根本的に変える

### 2-6-2: フライホイール

- ユーザー獲得 → 価値提供 → 収益・データ → 次のユーザー獲得、のループを描く
- **1 周目から回るか、N 周目から加速するのか**を必ず問う。1 周目が回らないループは、回り出すまでの資金・持久戦略が別途必要
- 2 点接続で弱ければ、入口 → 体験 → 完結 → 次の利用、のような多点接続を検討する

### 2-6-3: KSF（Key Success Factor）の特定

事業が成功するために**絶対に勝たなければならない 1〜3 個のポイント**を特定する。3 ステップ：

1. この事業の利益の源泉はどこか（何が一番お金を生むか）
2. その利益を生むために、ユーザーにどんな行動を取ってもらう必要があるか
3. その行動の障壁は何か

- KSF は「〜率」「〜数」のように **KPI（測る指標）に落とせる粒度**まで具体化する。「ブランド力」「技術力」のような抽象語で止めない（「もう一段下に降ろせる指標は何か」と問い直す）
- **5 個以上に増えたら、成功要因ではなく施策リストを並べているサイン** — 利益源泉との因果に戻って 1〜3 個へ絞る
- 各 KSF への打ち手を 3 つ以上出し、打ち手同士のトレードオフがあれば指摘する

## 2-7: Why Now（タイミング論）

「やる事業」と同じくらい「やる時期」で勝敗が決まる。追い風を 6 タイプで棚卸しする：

| 追い風タイプ | 確認の問い |
|---|---|
| 規制変化 | 法改正・許認可・自主規制で参入障壁が動いたか |
| 技術成熟 | 必要技術のコスト・精度が事業成立水準に達したか（生成 AI 含む） |
| 世代交代・価値観変化 | 価値観の変化が市場を反転させたか |
| 流通構造の変化 | 顧客への導線コストが構造的に変わったか |
| コスト曲線の変曲点 | 主要コストが成立しきい値を割ったか |
| ライフスタイル変化 | 生活の構造変化が新しい需要を生んだか |

**合格基準**: 「**なぜ 3 年前ではダメで、3 年後では遅いのか**」を 1 文で言い切れること。言い切れなければ追い風の特定からやり直す。補助基準として、**自分・自社の固有アセットが直近で使える状態になった**（段階変化）ことを 1 文で言い切れる場合も合格とする。

## 2-8: 収益モデルと支払い意思

1. **ビジネスゲーム 3 分類の宣言**: この事業は何で価値が積み上がるか — **Attention（注目・時間）/ Transaction(取引量) / Productivity（顧客の生産性・成果）** のどれかを即答する。即答できない = 収益モデル未定義の露呈
2. **WTP（支払い意思額）の導出**: 希望価格や業界相場からではなく、**2-3 で定量化した代替手段のコスト（現状ワークアラウンドに払っている金銭・時間）をアンカー**に、いくらまでなら乗り換えるかを推計する（数値ラベル必須）
3. **ユニットエコノミクスの桁感**: 顧客獲得コスト（CAC）と顧客生涯価値（LTV）を桁感で置き、**LTV > 3 × CAC** が描けるかを確認する。描けない場合は価格・獲得チャネル・継続構造のどれを直すかを議論する
4. **Trade-offs（やらないこと）の明文化**: この収益モデルを成立させるために意図的に捨てるもの（対象外セグメント・提供しない機能・追わない売上）を 2〜3 行で書く

## 2-9: 仮定の洗い出し（8 リスクカテゴリ）

深掘りの最後に、この案が依存している仮定を 8 カテゴリで網羅的に洗い出す。**盲点はたいてい Value 以外（特に Go-to-Market と Viability）にある**：

| カテゴリ | 問い |
|---|---|
| Value（価値） | 顧客に価値を生むか。使い続けるか |
| Usability（使い勝手） | 使い方が分かるか。オンボーディングできるか |
| Viability（事業成立性） | 売れるか・儲かるか・サポートできるか・法令を満たすか |
| Feasibility（実現性） | 今の技術・体制で作れるか。スケールするか |
| Ethics（倫理） | そもそもやるべきか。顧客・社会にリスクを生まないか |
| Go-to-Market（市場到達） | 顧客に届けるチャネルがあるか。試してもらえるか。今がその時か |
| Strategy（戦略） | 他社に真似されたら終わりではないか。解くべき問題として最良か |
| Team（体制・軽量） | 推進する人・時間・スキルはあるか |

各仮定に**確信度（高 / 中 / 低）**を付け、Phase 1 の「鍵となる仮定」を更新する。ここで出た低確信度・高影響の仮定が Phase 3 の Red-team と検証プラン表の主入力になる。

## Phase 2 の出口

案ごとに notes へ「## Phase 2 深掘り 確定（YYYY-MM-DD）」セクションを書き出す。含めるもの（**実施した手順の成果物のみ必須**。未実施の手順の項目は捏造せず「未実施（Quick モード）」または「未実施（ユーザー判断）」と明記して項目自体は残す）：

- Quick 必須セット分（常に必須）: Job Story 1 文（2-1）/ 課題実在性 3 点の答え（2-3）/ Why Now 1 文（2-7）/ 収益モデルの 3 分類と WTP アンカー（2-8）
- 実施した場合のみ: ビーチヘッドと失格基準（2-4）/ 価値提案 6 パーツ（2-5）/ 構造類型と KSF（2-6）/ LTV/CAC 桁感（2-8 手順 3）/ 更新済みの鍵となる仮定リスト・確信度付き（2-9）
- handoff manifest（note-templates.md の書式。空欄禁止。未実施項目のうち評価に効きそうなものは「未解決論点」に挙げる）

複数案を深掘りした場合は、全案の確定後に比較表（案 × KSF × Why Now × LTV/CAC 桁感 × 最大の未確認仮定）を提示し、AskUserQuestion で Phase 3 に進める案を確認する。
