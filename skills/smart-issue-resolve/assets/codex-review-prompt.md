## レビュー観点

- **仕様充足**: Issue の要件・受け入れ基準を満たしているか
- **バグ**: ロジック誤り・エッジケース・境界条件・エラーハンドリング漏れ
- **回帰リスク**: 既存の挙動・テスト・呼び出し元を壊す変更はないか
- **実装レベルの危険箇所**: インジェクション・秘密情報の混入・認可漏れ・依存脆弱性
- **運用・保守・可用性**: 可観測性（ログ・メトリクス・アラート）の欠落、デプロイ/ロールバック・設定管理のしやすさ、保守性（過度な結合・テスト容易性・変更波及）、可用性（タイムアウト・リトライ・障害時の劣化・リソース枯渇・単一障害点）
- **データ整合性・性能**: トランザクション境界・原子性・冪等性（二重実行防止）・並行更新時の整合性、N+1・不要な全件取得・過剰なラウンドトリップ・計算量
- **テストカバレッジ**: 新規/変更ロジックに対する検証の網羅（正常系・異常系・境界値）が十分か
- **アーキテクチャ境界**: レイヤー責務の逸脱・境界侵犯（上位層へのドメインロジック漏れ、層をまたぐ不正な依存など）
- **プロジェクト固有基準との整合**: 「5. プロジェクト固有基準」に反していないか（提示がなければ本観点はスキップ）。※ 可読性・命名・スタイルは引き続き対象外

## 制約

- 可読性・命名・スタイルの指摘は対象外（修正価値のある欠陥のみ）
- 各指摘に根拠（ファイルパス・行番号など一次情報）と重大度（High / Medium / Low）を付ける
- 指摘が 1 件もなければ「指摘なし」とだけ返す
- コードやファイルの変更は行わない（レビューのみ）

## 呼び出し時の注意

- このテンプレート全体を埋めたうえで渡す。**Claude Code ホスト**では Skill ツールの `codex:rescue` に task として渡す。**Codex CLI ホスト**（本 skill 自体を Codex CLI が実行している。`codex:rescue` は存在しない）では `codex exec`（非対話・毎回新規セッション）を起動する — 具体的な起動手順・失敗時の診断は下記「Codex CLI ホストでの補足」に必ず従う（ホストのサンドボックス内では起動できない・stdin リダイレクト漏れで無応答になる等、既知の落とし穴がある）。いずれの経路でも、実装を行っている現在のセッションとは独立した新規セッションでレビューを取得し、同一セッション内で自己レビューを完結させない
- Codex はリポジトリにアクセスできるため、diff の取得・コードの確認は Codex 側に行わせる（巨大な diff を依頼文に貼り込まない）
- Codex にコードの修正を行わせない（レビューのみ）。修正は Claude 側の妥当性判定を経てから行う
- 返ってきた指摘の再解釈・要約による弱体化をしない（妥当性判定は採用 / 不採用の分類と理由の明記のみ）

## 運用ノート: silent death（ハング・静止死）からの復旧（Claude Code ホスト / codex:rescue 経由）

Codex のレビュープロセスは、ジョブレジストリ上 `running` のまま静かに死ぬことがある。レビュー結果がいつまでも返らない場合は、フォールバックに切り替える前に以下の順で復旧を試みる:

1. **検知（stall 判定）** — 次の 3 点が揃えば stall 確定: ジョブの `updatedAt` が固定のまま（`elapsed` だけ進行）/ `kill -0 <pid>` が失敗 / ジョブログの mtime が停止
2. **回収** — rollout transcript（`~/.codex/sessions/YYYY/MM/DD/rollout-*-<threadId>.jsonl`）の末尾を確認する。`agent_message` / `task_complete` があれば実は完了済みなので、そこから結果を回収する。末尾が `reasoning` / `function_call` で途切れていたら未完（silent death）
3. **復旧（resume が最効率）** — companion の cancel（`/codex:cancel`）で stale ジョブを落とす → resume 候補が復活する（`task-resume-candidate` が `available: true` を返す）→ `--resume` を付けて `codex:rescue` を再投入する。調査コンテキストを引き継いで続きから実行されるため、fresh 再実行より大幅に速い
4. **予防** — companion を Bash で直接起動する経路では timeout を 600000ms（10 分）に明示する（デフォルト 120 秒では長いレビューが親側から切られる）。長時間が見込まれるレビューは `--background` 実行でプロセスのライフサイクルを呼び出し元の Bash から切り離すことを検討する

復旧（cancel → `--resume` 再投入）を 2 回試しても完了しない場合は、SKILL.md の「フォールバック（codex:rescue / codex exec が利用不能時）」に切り替える。

## Codex CLI ホストでの補足

`codex exec` は呼び出し元の shell 内で同期的に完了を待つ同期呼び出しで、上記の companion 側ジョブレジストリによる stall 検知・復旧手順の対象外である。起動手順（1 回のレビュー / 裁定ごと）:

1. 埋めたテンプレート全文を一時ファイルに書き出す（`mktemp` で OS の一時領域に作成。巨大な依頼文をコマンド引数で直接渡すと引用符・特殊文字で壊れるため必ずファイル経由にする）
2. 次の形で起動する:

   ```bash
   codex exec --sandbox read-only -C <リポジトリルート> -o <出力ファイル> - < <プロンプトファイル>
   ```

   - `-` は「プロンプトを stdin から読む」指定。**stdin をリダイレクトせずに実行すると入力待ちのまま無応答になる**（「レビュー / 裁定が返らない」の典型原因）
   - **ホストのコマンドサンドボックス内では `codex exec` は起動できない**（`failed to initialize in-process app-server client: Operation not permitted` で即失敗する — 実測）。**サンドボックス外での実行（昇格実行）を承認付きで要求して起動する**こと。ファイル保護は子プロセス自身の `--sandbox read-only` が担う
   - `--sandbox read-only` はレビュー / 裁定のみでファイル変更をさせないための明示
   - timeout は 600000ms（10 分）以上を明示する
3. 結果は stdout ではなく `-o` の出力ファイルから読む（stdout は進捗ログが混在し、timeout 打ち切り時には失われる）
4. `Not inside a trusted directory` エラーで即失敗した場合は、対象リポジトリが Codex の trusted directory に未登録 — `--skip-git-repo-check` を付けて再実行する

応答がなく完了しない・結果が空の場合は、(a) stdin リダイレクト漏れ (b) ホストサンドボックス内での起動（昇格の欠落） (c) timeout 不足 — の順で確認して再実行し、それでも完了しなければ「フォールバック（codex:rescue / codex exec が利用不能時）」に切り替える（silent death の複雑な復旧手順は適用しない）。
