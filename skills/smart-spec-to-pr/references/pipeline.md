# pipeline.md — Phase 2〜3 + 終点チェックリスト

> このファイルは `{作業Dir}/spec.md` に `## Phase 1 確定` セクションが存在することを確認してから Read する（SKILL.md の物理ゲート）。Phase 1 承認前に読み込まない。

Phase 2 以降は conductor が **Phase 3b まで**制御を保持し、Phase 3c/d でハンドオフ用ランブックを提示してターンを終える（SKILL.md「制御の実態」参照）。ハンドオフ後の結果分岐・ゲート強制・Issue 追跡は記述しない（到達不能）。

各フェーズの入口に**物理ゲート**を置く: 直前フェーズの成果物（Phase 2 の Issue 番号・Phase 3a の設計コメント）が確認できない状態で次フェーズへ進まない。

## Phase 2: Issue 起票

`{作業Dir}/spec.md` を Issue 本文の逐語正本として起票する。

1. **作成者の取得** — `get_me`（利用不能なら `gh api user`）で GitHub ユーザー名を取得する（作成者アサインに使う）
2. **重複チェック** — `search_issues` で spec タイトル相当のキーワードの既存 open Issue を検索し、重複起票を防ぐ
3. **既存 Issue ヒット時の分岐** — ヒットがあれば、AskUserQuestion で「既存 Issue を採用」か「新規作成」かを確認する:
   - **既存 Issue を採用して本文を上書きする場合** → 上書き前に、その Issue の**現タイトルと現本文（要約可）を提示**し、AskUserQuestion で「この Issue の本文を spec で上書きしてよいか」を明示確認する。**承認が得られたときのみ** `issue_write` で本文を更新する。承認が得られなければ新規作成へ切り替えるか中止する（無条件・自動の上書きはしない ＝ 無関係な Issue の本文破壊を防ぐ）
   - **新規作成を選んだ場合** → 手順 4 へ
4. **Issue 作成** — `issue_write` で Issue を作成する:
   - タイトル: spec の「概要」から簡潔に生成する
   - 本文: **`{作業Dir}/spec.md` の全文を逐語で**（要約・改変しない。以降の全スキルにとっての永続正本になる）
   - ラベル: リポジトリの既存ラベルから内容に適したものを付与する
   - アサイン: 手順 1 で取得した作成者を自動アサインする
5. **Issue 番号・URL の保持** — 作成（または採用）した **Issue 番号と URL を明示的に保持・提示**する（Phase 3 以降で参照し、ハンドオフ時のコマンドにも埋め込む）

> **物理ゲート（→ Phase 3a）**: Issue 番号が確定していない状態で Phase 3a へ進まない。

## Phase 3a: 設計（software-architect）

1. **設計の起動** — Skill ツールで `software-architect` を起動する（引数なし。直前の Issue 内容が会話コンテキストにあるため、それを要件として設計する）。`software-architect` は `disable-model-invocation` を持たないため conductor から Skill 起動できる唯一の連鎖先
2. **設計出力の永続化** — 設計出力はチャットのみで揮発するため、conductor が `add_issue_comment` で Phase 2 の Issue にコメントとして投稿し永続化する（`smart-issue-plan` は直近 5 件のコメントを読むため、次段 `/smart-issue-plan` の入力として届く）

> **物理ゲート（→ Phase 3b）**: 設計コメントの投稿が確認できない状態で Phase 3b へ進まない。

## Phase 3b: レビューモードの確定（ハンドオフ前に必須）

`{レビューループ指定}`（引数解析で検出）が**未指定**の場合、AskUserQuestion でレビューループモードを確定する。「**PR 作成まで自動で進めるにはレビューループ指定が必要**」である旨を明示して選ぶ:

| 選択肢 | コマンド 2 に付けるフラグ | 到達点 |
|---|---|---|
| Claude 標準（推奨デフォルト） | `--claude-review-loop` | 収束後にコミット・PR 自動作成 |
| Claude 敵対的 | `--claude-adv-review-loop` | 同上 |
| Codex 標準 | `--codex-review-loop` | 同上（Codex プラグイン前提） |
| Codex 敵対的 | `--codex-advs-review-loop` | 同上 |
| なし | （フラグなし） | PR 未到達。実装後の完了案内で止まる |

引数解析でフラグが指定済みなら、その `{レビューループ指定}` をそのまま採用する（再確認しない）。この確定は**コマンド 2 にフラグを埋め込むために必須**であり、ハンドオフ後には実施できない（3d より後に回さない）。

## Phase 3c/d: ハンドオフ（conductor の最終アクション）

次を「ユーザー向け手動ランブック + 終点チェックリスト」として**一括提示してターンを終える**。conductor はここで制御を手放すため、以降の分岐・強制はしない。

### 手動ランブック（順に実行）

**コマンド 1**（実装計画。フラグは渡さない）:

```
/smart-issue-plan #<Issue番号>
```

**コマンド 2**（実装 → レビューループ → PR。`<日付>` は Phase 1 確定の日付、`<slug>` は spec のスラグ、末尾は Phase 3b で確定したフラグ）:

```
/smart-issue-resolve #<Issue番号> -p "docs/specs/<日付>-<slug>-design.md を必須成果物として作成すること（省略・後回ししない。context の要件・受け入れ基準に沿って書く）" <確定したレビューループフラグ>
```

- **`-p` に spec 全文をインラインしない**。`smart-issue-resolve` の引数パーサは `$ARGUMENTS` 全体からフラグ語を位置無関係に検出・除去するため、`-p` テキストがフラグ語を含むと silent drop ＋ フラグ上書きが起きる。`-p` は上記の「design.md を必須成果物にする」指示に限定し、レビューループフラグは `-p` の外（末尾）に置く
- **「Issue 本文を正本とし要約・改変しない」という履行不能句を `-p` に書かない**。開発者エージェントには Issue 本文の要約しか届かない設計のため
- Phase 3b で「なし」を選んだ場合はコマンド 2 にフラグを付けない（PR には到達しない ＝ 下記チェックリスト参照）

### 終点チェックリスト（ユーザーが手動実行後に確認）

conductor は強制できないため、印字で提示する:

- **PR が作成された場合**（レビュー収束・打ち切りのいずれも）:
  1. 実行されたレビュー系統・モードが指定どおりか確認する
  2. PR に `docs/specs/<日付>-<slug>-design.md` が実在し、切り詰め版になっていないか確認する。欠落・切り詰めがあれば **Issue 本文（永続正本）から手動追補**する（自動生成は context 要約由来の切り詰め版になりうるため、この手動確認が正本経路）
- **レビューループ「なし」選択・フォールバック未実施の場合** → 終点（PR）未到達。`/smart-commit` → `/smart-pr` を手動実行する
- **下流の中止・失敗で PR 未到達の場合** → Phase 2 で起票した Issue が open のまま残る。再実行するか手動でクローズ判断する（conductor 側で自動クローズ・ロールバックはしない）
