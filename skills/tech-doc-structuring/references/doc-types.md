# 文書タイプ判定と見出しセット

## タイプ判定表

`--type` 指定 > frontmatter の `type` > 以下のシグナルの順で判定する。複数該当して決めきれない場合は AskUserQuestion で確認する（使えないエージェントではテキストで確認する）。

| シグナル（内容・ファイル名・置き場所） | type |
|---|---|
| 「採用する / 決定した」という単一の技術選定・方針決定が主題。`adr/`・`decisions/` 配下、`NNNN-` 接頭辞 | `adr` |
| 機能・システムの設計説明が主題（構成・データフロー・API 設計）。「設計書」「design」 | `design-doc` |
| 満たすべき要求・仕様の列挙が主題。「仕様書」「要件」「spec」「requirements」 | `spec` |
| 運用手順・障害対応手順が主題。「手順書」「runbook」「operations」 | `runbook` |
| 障害・インシデントの振り返りが主題。「障害報告」「postmortem」「incident」 | `postmortem` |

## タイプ別見出しセット

H1 = タイトル（唯一の正）。H2 を以下の順で置く。**該当する内容が無い章は見出しごと省略してよい**が、順序は入れ替えない。

### adr

| 見出し | 内容 |
|---|---|
| `## Context（背景）` | 決定が必要になった背景・課題・制約。何と何が衝突しているか |
| `## Decision（決定）` | 「X を採用する」の能動形。何を・どの範囲で・どうするか |
| `## Alternatives（検討した代替案）` | 案ごとに `### 案 N: <名前>`。内容と却下理由 |
| `## Consequences（結果と影響）` | 正負両方の影響・受け入れたトレードオフ・フォローアップ |

### design-doc

| 見出し | 内容 |
|---|---|
| `## 背景` | 解決したい課題・現状 |
| `## 目標と非目標` | スコープの線引き（やらないことを明記） |
| `## 設計概要` | 全体像。図があればここ |
| `## 詳細設計` | コンポーネント・データフロー・インターフェース |
| `## 代替案` | 検討した他の設計と採らなかった理由 |
| `## リスクと対策` | 既知のリスク・軽減策 |
| `## 未解決の論点` | 決めきれていないこと |

### spec

| 見出し | 内容 |
|---|---|
| `## 概要` | 対象と目的 |
| `## 用語` | 定義が必要な用語（列挙は表で OK） |
| `## 機能要求` | 機能として満たすべきこと |
| `## 非機能要求` | 性能・可用性・セキュリティ等 |
| `## 制約` | 前提・技術制約 |
| `## 受け入れ基準` | 検証可能な合否条件 |

### runbook

| 見出し | 内容 |
|---|---|
| `## 目的` | いつ・何のために実行する手順か |
| `## 前提条件` | 必要な権限・環境・事前確認 |
| `## 手順` | 番号付きステップ（コマンドはコードブロック） |
| `## 検証` | 成功をどう確認するか |
| `## ロールバック` | 失敗時の戻し方 |
| `## トラブルシューティング` | 既知の失敗パターンと対処 |

### postmortem

| 見出し | 内容 |
|---|---|
| `## 概要` | 何が起きたか（1 段落） |
| `## 影響` | 影響範囲・期間・ユーザー影響 |
| `## タイムライン` | 検知〜収束の時系列（列挙は表で OK） |
| `## 根本原因` | 因果の連鎖を散文で。責任追及ではなく構造の説明 |
| `## 対応` | 実施した応急対応・恒久対応 |
| `## 再発防止策` | アクションアイテム（担当・期限があれば明記） |

### 上記に該当しない文書

見出しの正規化はせず、frontmatter の付与（`type` は付けない。status / date / tags / related のみ）と見出しレベルの整合（H1 が 1 つ、階層の飛びなし）だけを行う軽量整形とする。
