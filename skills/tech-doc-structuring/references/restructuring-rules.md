# 整形（restructuring）規則

既存文書をハイブリッド構造へ正規化するときの詳細規則。**ロスレス**（情報を失わない）が最優先で、構造の綺麗さのために内容を犠牲にしない。

## 原則

1. **移動はしても削除はしない** — frontmatter へ移した情報の本文側の重複行だけを除去する。それ以外の本文は削らない
2. **文体を変えない** — 散文は散文のまま、箇条書きは箇条書きのまま。要約・言い換え・追記をしない
3. **迷ったら退避** — どの標準見出しにも割り当てられない節は `## 補足`（文書末尾に置く）の下へ原文のまま移す（勝手に捨てない・無理に割り当てない）。退避する節は元の見出しを 1 レベル降格して保持する（H2 → H3）
4. **既存 frontmatter とはマージ** — 既にあるキーの値は保持する。標準キーと矛盾する場合（例: `state:` と `status:` の併存）はユーザーに確認する

## メタデータの抽出（本文 → frontmatter）

| 本文中のパターン | 移動先 |
|---|---|
| `Status: Accepted` / 「状態: 承認済み」などの単独行・節 | `status`（値域へ正規化: 承認済み → `accepted` 等） |
| 日付の単独行（`Date:` / 「作成日:」 / 「決定日:」） | `date` |
| 「関連:」 / 「参照:」 / `See also:` の文書リンク列挙 | `related`（説明文付きの参照は本文に残す） |
| 決定者・承認者の列挙行 | `deciders`（ADR）/ `owners`（その他） |
| タグ・カテゴリの列挙行 | `tags` |

- 値の正規化で情報が落ちる場合（例: `Status: 一部承認`）は、frontmatter には最も近い標準値を入れ、原文を `## 補足` に残す
- 本文から抽出できるメタデータが無い場合: `date` はファイルの git 初回コミット日（取得できなければ当日・JST）を使い、`status` は内容から推定した値を提案してユーザーに確認する

## 見出しのマッピング

| 既存見出しの例 | 標準見出し（adr の場合） |
|---|---|
| 背景 / 課題 / 経緯 / Motivation / Why | `## Context（背景）` |
| 決定 / 結論 / 採用案 / 方針 / Decision | `## Decision（決定）` |
| 代替案 / 却下案 / 比較検討 / Considered Options | `## Alternatives（検討した代替案）` |
| 影響 / 結果 / トレードオフ / Pros-Cons / Consequences | `## Consequences（結果と影響）` |

- adr 以外のタイプも同様に、意味の対応で references/doc-types.md の見出しセットへマッピングする
- 1 つの既存節に複数の標準見出しへまたがる内容が含まれる場合、段落単位で分割してよい（文の分割・書き換えはしない）
- 章の順序は標準見出しセットの定義順に並べ替える

## 書き込みと報告

- 変更計画（メタデータ移動・見出しマッピング・退避する節）をすべて洗い出してから、1 ファイル 1 回の Edit / Write で完結させる
- 差分要約として「frontmatter へ移動した項目 / 見出しの対応表 / `## 補足` へ退避した節 / ユーザー確認が必要だった判断」を報告する
- 元ファイルのパス・ファイル名は変えない（ADR の採番・リネームは整形の範囲外）
